# Phase 5.5 — Cyberpunk polish: implementation spec

Design approved 2026-09-25. Implements the Phase 5.5 section of `ROADMAP.md`.

Source of truth for `apps/web` and `apps/mobile`. The interactive proof of concept (a single
self-contained HTML page, not in the repo) is published at
<https://claude.ai/artifact/32CancxRN7HWtmZ2AeCpJt>. Every number below is the one the POC uses.
When the POC and this file disagree, this file wins. "The POC" below always means that page.

Scope: the three Phase 5.5 bullets **Cyberpunk font**, **Given vs. player digits** and
**Unit-complete effects**, plus the chirp's sound design (needed by the mobile audio port).
The rest of the mobile animation and sound port is out of scope here.

## 1. Decisions

| # | Decision | Rationale | Rejected |
|---|----------|-----------|----------|
| D1 | **Orbitron** (display) + **Oxanium** (UI, HUD, grid digits) | Oxanium's digits are all 0.578 em wide by default, so the timer and counters can't jitter. It has real weights from 200 to 800, which gives givens a heavier weight. Its squared, open forms stay legible at 22–23 px in a 38–40 px cell. | **Audiowide + Chakra Petch.** Chakra Petch digits range from 0.358 to 0.628 em and the font has no `tnum` feature, so the timer shuffles. It's the runner-up if the owner prefers its look, but every numeric readout would need a fixed-width box per character. **Share Tech Mono.** Only one weight (400), so givens can't be heavier and the distinction would rest on colour alone. **Audiowide as display.** It works, but Orbitron's wider and more geometric caps read as "2077" more clearly. |
| D2 | Givens are "hardwired": `#F3F5FE`, weight 700, persistent cell tint. Player digits are "injected": `#B5ABFC` (accent-400), weight 400, no tint. | Two independent cues (weight and hue) plus a background cue. Each holds when the others are neutralised. | accent-300 `#D2CEFD` for player digits (the mobile value today): too close to white at a glance. accent `#9184D9`: only 5.1:1 on the selected background, and it looks dim. |
| D3 | Highlights (peer, same value, selected, conflict) are a **background layer** drawn over the given tint. Digit colour never changes, except that a **player** digit in conflict turns red. | Keeps the given/player distinction through every state. This fixes the web bug where same-value recolours both digits to accent-300. | Recolouring digits on same value (today's web behaviour). |
| D4 | **Departure:** a **given** in conflict keeps its white digit and gets only the red background. | A given can't be the mistake. Turning it red points at the wrong cell, and the white digit keeps it readable as "fixed". The recommendation said "only conflict turns the digit red"; this narrows that to player digits. | Red digit for both. |
| D5 | Unit complete = all 9 cells filled **and none of them is in the conflict set** (the board-wide peer-conflict set, not just duplicates inside the unit). | This stops the effect from celebrating a move that clashes with a peer outside the unit. | Checking duplicates inside the unit only. |
| D6 | One effect primitive: **an expanding neon ring centred on the changed cell, clipped to the union of the newly completed units.** | Clipped to a row, the ring reads as a horizontal sweep outward from the cell. Clipped to a column, it's a vertical sweep. Clipped to a box, it's a box sweep. Clipped to a union, it's the merged pulse, which is one animation by construction. The same code serves web canvas and a Flutter `CustomPainter`. | Separate row, column and box animations with a merge rule (three code paths per client, and stacking bugs). Always sweeping left to right (loses the link between cause and effect). |
| D7 | Boxes additionally get a **corner-bracket flash** (reusing the frame's `CornerBrackets` motif) and then a persistent **scanline hatch** ("sector secured"). Rows and columns get the sweep only. | **Departure:** the persistent tint is a hatch (1 px lines every 3 px), not a flat tint. A flat violet tint was indistinguishable from the peer highlight (both are violet at about 9%). The hatch reads as a different kind of mark and stays faint. | A flat accent tint at 5–8% (collides with the peer highlight). Green (implies "correct", which the client can't know). |
| D8 | The persistent hatch is **derived state** (`securedBoxes(grid)`), not an event. | Undo, erase, resume from storage and conflict resolution all just work. There's nothing to roll back. | Storing tint flags in history. |
| D9 | Wording: "complete" and "secured". Never "correct", "solved" or "right". | Under peer-conflict rules, "complete" ≠ "correct". | — |
| D10 | Chirp: triangle-wave blips with an upward glide, one per unit completed (1–3), stepping E5 → A5 → C♯6. It **replaces** the place blip on that move. | Short, bright, and clearly "more" for more units. Replacing the place blip avoids two sounds on one move. | Layering the place blip and the chirp. |
| D11 | **Signal yellow** `#FCEE0A` as a second accent. Violet is **state** (player digits, selection, highlights, secured hatch). Yellow is **signal**: the sweep ring's leading edge (the trail stays violet), box bracket flash, primary buttons (yellow fill, `#161826` ink, 8 px clipped corners), the event/log line, the combo and sectors counters, the `2077` in the logo, section eyebrows and the board's outer frame corners. Digits are never yellow. | Adds the signature cyberpunk yellow, and it's complementary to violet, so the two don't compete. Keeping it off the digits preserves the D2 given/player split. The POC has an Accent switch to compare. | Yellow player digits (a board full of yellow is loud, and yellow vs. white is a weak split at small sizes). Yellow as the only accent (loses the Nocturne identity). Yellow selection (it would read as an event, not state). |

|---|---|---|---|

## 4. Unit-complete detection and effects

### 4.1 Pure functions (shared semantics; TypeScript shown, Dart is a line-by-line port)

Put these in `packages/sudoku-core/src/units.ts` and export them from `index.ts`, so the rule
lives next to `peersOf` and gets unit tests. Mobile ports them to `lib/domain/units.dart`.

```ts
export type UnitKind = "row" | "col" | "box";
export interface Unit { kind: UnitKind; index: number } // index 0..8

export function unitCells(u: Unit): number[] {
  const out: number[] = [];
  for (let k = 0; k < 9; k++) {
    if (u.kind === "row") out.push(u.index * 9 + k);
    else if (u.kind === "col") out.push(k * 9 + u.index);
    else {
      const br = Math.floor(u.index / 3) * 3, bc = (u.index % 3) * 3;
      out.push((br + Math.floor(k / 3)) * 9 + bc + (k % 3));
    }
  }
  return out;
}

export const ALL_UNITS: Unit[] = (["row", "col", "box"] as const)
  .flatMap((kind) => Array.from({ length: 9 }, (_, index) => ({ kind, index })));

/** Board-wide peer-conflict set, the same rule useBoardState already uses. */
export function conflictSet(grid: Grid): Set<number> {
  const out = new Set<number>();
  grid.forEach((v, i) => { if (v !== 0 && peersOf(i).some((p) => grid[p] === v)) out.add(i); });
  return out;
}

/** Complete = all 9 filled and none in conflict. NOT "correct": the client has no solution. */
export function completeUnits(grid: Grid, conflicts = conflictSet(grid)): Unit[] {
  return ALL_UNITS.filter((u) =>
    unitCells(u).every((i) => grid[i] !== 0 && !conflicts.has(i)));
}

/** Units complete in `next` but not in `prev`, ordered row, col, box. */
export function newlyCompletedUnits(prev: Grid, next: Grid): Unit[] {
  const key = (u: Unit) => `${u.kind}${u.index}`;
  const before = new Set(completeUnits(prev).map(key));
  return completeUnits(next).filter((u) => !before.has(key(u)));
}

export function securedBoxes(grid: Grid): Set<number> {
  return new Set(completeUnits(grid).filter((u) => u.kind === "box").map((u) => u.index));
}
```

Notes on the algorithm:
- All 27 units are compared (27 × 9 reads, trivially cheap), not only the three units that contain the changed cell. Overwriting a player digit, or erasing one, can clear a conflict elsewhere and complete a unit that doesn't contain the changed cell. The pulse still originates at the changed cell, and the ring clip still shows only the completed units.
- A normal placement completes at most 3 units (its row, column and box).
- Max-mistakes and game over: no effect is fired when `setCell` is refused.

### 4.2 Event and effect rules

In the `SET_CELL` handler (web reducer, mobile `BoardState.setCell`):

```
units = newlyCompletedUnits(prevGrid, nextGrid)
isWin = nextGrid has no 0 && conflictSet(nextGrid) is empty
if units.length > 0 && !isWin:
    lastCompletion = { id: ++seq, origin: index, units }
```

- **Undo** never produces a completion event. Set `lastCompletion = null`, cancel running effects, and let the hatch fade out through derived state.
- **Winning move:** the win flow (win sound, confetti or burst, dialog) replaces the effect entirely: no ring, no bracket flash, no chirp (owner decision Q3, section 8). The POC still runs the ring there; it predates that decision.
- **Resume from storage:** the hatch appears immediately from derived state, with no sweep.
- **Screen readers:** announce `"Row 3 complete"`, `"Column 7 complete"` or `"Box 5 complete"` in the existing live region (web `aria-live="polite"`, Flutter `SemanticsService.announce`). The effect itself has no visible text.

Ring rendering, per frame, `t = elapsed / duration` in [0, 1]:

```
cells   = union of unitCells(u) for u in units
cw      = cell side (px)
O       = centre of origin cell
Rmax    = max distance from O to any corner of any cell in `cells` + 1.6·cw
R       = Rmax · easeOutCubic(t)
lead    = 0.35·cw        trail = 1.6·cw        outer = R + lead
a       = 0.70 · (1 − t²)

clip to the union of the cell rects (so the box/cell separator lines stay unlit)
fill clip with accent  @ 0.14·(1 − t)                      // base flash
fill clip with radial gradient centred at O, radius `outer`:
  stop 0                          accent   @ 0
  stop sT = max(0,(R−trail)/outer) accent   @ 0
  stop (sT+sC)/2                   accent   @ 0.45·a
  stop sC = R/outer (≥ sT+0.001)   #E7E5FE  @ a
  stop 1                           #E7E5FE  @ 0
```

For each box in `units`, trigger the bracket flash (2.4) at the same moment.
Duration: 420 ms if `units.length == 1`, otherwise 560 ms. With reduced motion, use the 300 ms substitute.

## 5. Sound

Existing SFX stay as they are (`place` 880 Hz sine 80 ms, `error` 140 Hz sawtooth 200 ms, `notesToggle`, `win`).

**Unit chirp**, `count` = number of units completed (1–3):

| Parameter | Value |
|---|---|
| Oscillator | `triangle` |
| Blip *k* (0-based) start | `now + k × 70 ms` |
| Base frequency *k* | 659.25 Hz (E5), 880.00 Hz (A5), 1108.73 Hz (C♯6) |
| Pitch glide | `setValueAtTime(f)`, then `exponentialRampToValueAtTime(f × 1.26, t + 60 ms)` (about +4 semitones) |
| Envelope | gain 0 → **0.22** linear over 5 ms, then exponential to 0.0001 at 120 ms |
| Stop | `t + 140 ms` |
| Total length | 140 / 210 / 280 ms for 1 / 2 / 3 units |

```ts
// sfx.ts
export function playUnitChirp(count: number): void {
  const ctx = getAudioContext();
  const notes = [659.25, 880, 1108.73];
  for (let k = 0; k < Math.min(count, 3); k++) {
    const t = ctx.currentTime + k * 0.07, f = notes[k];
    const o = ctx.createOscillator(), g = ctx.createGain();
    o.type = "triangle";
    o.frequency.setValueAtTime(f, t);
    o.frequency.exponentialRampToValueAtTime(f * 1.26, t + 0.06);
    o.connect(g); g.connect(ctx.destination);
    g.gain.setValueAtTime(0, t);
    g.gain.linearRampToValueAtTime(0.22, t + 0.005);
    g.gain.exponentialRampToValueAtTime(0.0001, t + 0.12);
    o.start(t); o.stop(t + 0.14);
  }
}
```

**Assets for Flutter:** render the patches with `OfflineAudioContext` (mono, 44.1 kHz)
from the same `sfx.ts` code, for example with a small `scripts/render-sfx.mjs` that drives headless Chromium through Playwright and
writes 16-bit PCM WAVs. Output: `unit_chirp_1.wav`, `unit_chirp_2.wav`, `unit_chirp_3.wav`, plus
`place.wav`, `error.wav`, `notes_toggle.wav` and `win.wav` for the rest of the port. Add 20 ms of silence at the end of each file.
Commit the WAVs, since they are small (each under 30 KB).

**Haptic (mobile):** `HapticFeedback.lightImpact()` once per completion event, whatever the count.

## 9. Mobile implementation notes (2026-09-25)

Where `apps/mobile` departs from the letter of sections 2–7, and why. The web port should make the same
calls unless noted.

- **Brackets are signal yellow** (D11), not the `accent-300` in 2.4 and 7.5.
- **Fonts** come from the upstream repos' own static builds (`sevmeyer/oxanium`, `googlefonts/orbitron-vf`),
  because `google/fonts` now ships only the variable files. Orbitron has a Reserved Font Name, so the
  statics are not re-instanced locally. There are two licence files, `OFL-Oxanium.txt` and
  `OFL-Orbitron.txt`, because their copyright lines differ. Neither font has a `tnum` feature, but every
  Oxanium digit is 578 units wide, so figures are tabular anyway.
- **Chirp assets** are rendered by a pure-Dart script, `apps/mobile/tool/render_chirps.dart`, rather than
  through Playwright and `OfflineAudioContext`. It evaluates the same oscillator (band-limited triangle),
  glide and envelope sample by sample, and a test checks the committed WAVs against it. Only the three
  chirps are rendered, because the other SFX belong to the later mobile sound port. Mobile has no place
  sound yet, so the chirp has nothing to replace.
- **Layer order.** The hatch and the ring are painted over the digits, as in the POC (`z-index`), rather
  than under them as 2.2 lists. At 13 % and a short fade they don't hurt legibility, and it keeps each one
  a single overlay.
- **Event line.** It uses the POC's wording and colours: yellow for every event, red for a clash. Oxanium
  has no `←`, so a placement reads `R3C4 <- 7`.
- **HUD** is two rows (tier and pause, then TIME / MISTAKES / COMBO / SECTORS) so it fits at 360 px.
- **Reduced motion.** Effect controllers use `AnimationBehavior.preserve`. Otherwise Flutter would also
  shrink the 300 ms substitute to 5 % of its length.
- `BoardState` also exposes `lastEvent` (placed, clash, erased, completed, full grid, undo) for the event
  line, next to the spec's `lastCompletion`.
